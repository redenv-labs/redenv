**Service Tokens** are the recommended way for applications and CI/CD pipelines to access secrets without using your Master Password.

## What is a Service Token?

A Service Token consists of two parts:

- **Token ID**: Public identifier (e.g., `tok_abc123`)
- **Secret Key**: Encrypted copy of the Project Encryption Key (e.g., `redenv_sk_xyz...`)

The Secret Key allows an application to decrypt secrets, but is **scoped** and can be revoked at any time.

## Creating Tokens

Create a new Service Token:

```bash
redenv token create my-app-production
```

Output:

```
✔ Token created successfully!

Token ID: tok_abc123
Token Key: redenv_sk_xyz789abcdefghijklmnopqrstuvwxyz...

⚠️  Save this token key! It will NOT be shown again.
```

<Callout type="error">
  **The Secret Key is shown only once!** Store it immediately in your password
  manager or deployment environment.
</Callout>

### Read-Only Tokens

For applications that only need to read secrets:

```bash
redenv token create my-app-production --read-only
```

Read-only tokens:

- ✅ Can decrypt and read secrets
- ✅ Can access version history
- ❌ **Cannot** add/edit/remove secrets

This limits the blast radius if a token is leaked.

<Callout type="info">
  **Best Practice**: Use read-only tokens for all production applications unless
  they explicitly need to write secrets.
</Callout>

## Listing Tokens

View all tokens for the current project:

```bash
redenv token list
```

Output:

## Revoking Tokens

Immediately invalidate a token:

```bash
redenv token revoke tok_abc123
```

After revocation:

- The token can no longer decrypt secrets
- Applications using it will fail authentication
- The token ID is removed from the project metadata

<Callout type="warn">
  **This is immediate and cannot be undone.** Make sure you've updated all
  applications using the token before revoking.
</Callout>

## Using Tokens in Applications

### JavaScript/TypeScript

```typescript
import { Redenv } from "@redenv/client";

const redenv = new Redenv({
  project: "my-app",
  environment: "production",
  tokenId: process.env.REDENV_TOKEN_ID!, // tok_abc123
  token: process.env.REDENV_TOKEN_KEY!, // redenv_sk_xyz...
  upstash: {
    url: process.env.UPSTASH_REDIS_URL!,
    token: process.env.UPSTASH_REDIS_TOKEN!,
  },
});

const secrets = await redenv.load();
```

### Python

```python
import os
from redenv import Redenv

client = Redenv({
    "project": "my-app",
    "environment": "production",
    "token_id": os.getenv("REDENV_TOKEN_ID"),    # tok_abc123
    "token": os.getenv("REDENV_TOKEN_KEY"),      # redenv_sk_xyz...
    "upstash": {
        "url": os.getenv("UPSTASH_REDIS_URL"),
        "token": os.getenv("UPSTASH_REDIS_TOKEN")
    }
})

secrets = await client.load()
```

## Token Storage

### Local Development

Store in a `.env.local` file (gitignored):

```bash
REDENV_TOKEN_ID=tok_abc123
REDENV_TOKEN_KEY=redenv_sk_xyz...
UPSTASH_REDIS_URL=https://...
UPSTASH_REDIS_TOKEN=...
```

### Production (Vercel)

Add as environment variables in the Vercel dashboard:

```
REDENV_TOKEN_ID=tok_abc123
REDENV_TOKEN_KEY=redenv_sk_xyz...
```

### CI/CD (GitHub Actions)

Store as repository secrets:

```yaml
- name: Deploy
  env:
    REDENV_TOKEN_ID: ${{ secrets.REDENV_TOKEN_ID }}
    REDENV_TOKEN_KEY: ${{ secrets.REDENV_TOKEN_KEY }}
  run: |
    # Your deployment script
```

## Token Security

### What Tokens Protect

✅ **No Master Password exposure**: Applications never see your Master Password
✅ **Revocable**: Instantly disable access without changing secrets
✅ **Scoped**: Read-only tokens limit damage if leaked
✅ **Auditable**: See which tokens exist and when they were created

### Token Leakage Response

If a token is leaked:

1. **Immediately revoke** the token:

   ```bash
   redenv token revoke tok_abc123
   ```

2. **Create a new token**:

   ```bash
   redenv token create replacement-token --read-only
   ```

3. **Update your deployment** with the new token

4. **Consider rotating secrets** if the leaked token had read-write access

<Callout type="info">
  **Good news**: Revoking a token does NOT require changing your secrets or
  redeploying your application with new secret values. You only need to update
  the token itself.
</Callout>

## Token Naming Best Practices

Use descriptive names that indicate:

- **Environment**: `prod`, `staging`, `dev`
- **Purpose**: `app`, `ci-cd`, `backup-script`
- **Owner**: `github-actions`, `vercel-deploy`

**Examples:**

- `app-production-readonly`
- `ci-cd-staging`
- `backup-script-readwrite`
- `vercel-prod-app`

## Token Rotation

**Recommended rotation schedule:**

- **Production tokens**: Every 90 days
- **CI/CD tokens**: Every 180 days
- **Development tokens**: Annually

**Rotation process:**

1. Create new token with same permissions
2. Update application/CI environment variables
3. Verify application works with new token
4. Revoke old token

## Read-Only vs. Read-Write

| Feature          | Read-Only                 | Read-Write                               |
| ---------------- | ------------------------- | ---------------------------------------- |
| Load secrets     | ✅                        | ✅                                       |
| Access history   | ✅                        | ✅                                       |
| Add/edit secrets | ❌                        | ✅                                       |
| Remove secrets   | ❌                        | ✅                                       |
| Use case         | Production apps, CI reads | Feature flags, dynamic config, CI writes |

<Callout type="info">
  **Most applications should use read-only tokens.** Read-write tokens are
  primarily useful for: - Feature flag services that update Redenv - Admin
  dashboards - Automated secret rotation scripts
</Callout>

## Token Limits

- **Max tokens per project**: Unlimited
- **Token revocation**: Instant
- **Token key length**: 256 characters (fixed)
