Redenv supports multiple **environments** within a single project, allowing you to maintain separate configurations for development, staging, production, and more.

## What is an Environment?

An environment is a isolated namespace for secrets within a project. Think of it as a separate `.env` file, but centralized and encrypted.

**Examples:**

- `development`: Local development secrets
- `staging`: Pre-production testing
- `production`: Live application secrets
- `test`: CI/CD test environment

Each environment has its own complete set of secrets with independent version histories.

## Creating Environments

When you register a project, a `development` environment is created by default:

```bash
redenv register my-app
# Creates project "my-app" with "development" environment
```

To add more environments, simply switch to them (they're created automatically):

```bash
# Switch to production (creates it if it doesn't exist)
redenv switch env production
```

<Callout type="info">
  Environments are created on-demand when you first switch to them or add
  secrets.
</Callout>

## Switching Environments

The `switch env` command changes your active environment:

```bash
# Switch to development
redenv switch env development

# Switch to production
redenv switch env production

# Switch to custom environment
redenv switch env qa-testing
```

Your current environment is stored in the `.redenv` file:

```json
{
  "name": "my-app",
  "environment": "production" // Current active environment
}
```

<Callout type="warn">
  The `.redenv` file tracks your **local** environment preference. Other team
  members can work in different environments simultaneously.
</Callout>

## Managing Secrets Per Environment

Once you've switched environments, all secret commands operate on that environment:

```bash
# Switch to development
redenv switch env development
redenv add API_KEY "sk_test_123"
redenv add DATABASE_URL "postgresql://localhost/dev_db"

# Switch to production
redenv switch env production
redenv add API_KEY "sk_live_xyz"
redenv add DATABASE_URL "postgresql://prod-host/prod_db"
```

Now you have different values for the same key across environments:

- `development.API_KEY` = `"sk_test_123"`
- `production.API_KEY` = `"sk_live_xyz"`

## Using Environments in Applications

Your application specifies which environment to load via the SDK configuration:

<Tabs items={['JavaScript/TypeScript', 'Python']}>
  <Tab value="JavaScript/TypeScript">
    ```typescript
    import { Redenv } from "@redenv/client";

    const redenv = new Redenv({
      project: "my-app",
      environment: process.env.NODE_ENV || "development", // Dynamic!
      tokenId: process.env.REDENV_TOKEN_ID!,
      token: process.env.REDENV_TOKEN_KEY!,
      upstash: { ... }
    });
    ```

    **Best Practice**: Use `process.env.NODE_ENV` or a similar mechanism to automatically select the environment.

  </Tab>
  
  <Tab value="Python">
    ```python
    import os
    from redenv import Redenv

    client = Redenv({
        "project": "my-app",
        "environment": os.getenv("ENV", "development"),  # Dynamic!
        "token_id": os.getenv("REDENV_TOKEN_ID"),
        "token": os.getenv("REDENV_TOKEN_KEY"),
        "upstash": { ... }
    })
    ```

  </Tab>
</Tabs>

## Environment Isolation

Environments are completely isolated:

✅ **Secrets don't overlap**: Changing `API_KEY` in `development` won't affect `production`
✅ **Independent versioning**: Each environment has its own version history
✅ **Separate tokens**: You can create environment-specific Service Tokens

## Common Environment Patterns

### 1. Three-Tier (Classic)

```
my-app
├── development (local dev)
├── staging     (pre-production)
└── production  (live)
```

### 2. Feature Branching

```
my-app
├── development
├── feature-auth (dedicated to a feature branch)
├── feature-payments
└── production
```

### 3. Multi-Region

```
my-app
├── development
├── production-us-east
├── production-eu-west
└── production-ap-south
```

### 4. Customer-Specific

```
my-app
├── development
├── prod-customer-a
├── prod-customer-b
└── prod-customer-c
```

## Cloning Environments

To copy all secrets from one environment to another:

```bash
# Clone production -> staging
redenv clone production staging
```

This is useful for:

- Setting up new environments
- Refreshing staging with production data
- Creating test environments

<Callout type="warn">
  **Be careful!** Cloning will **overwrite** all secrets in the target
  environment. This operation cannot be undone (but you can rollback individual
  secrets).
</Callout>

## Comparing Environments

See what's different between environments:

```bash
redenv diff development production
```

Output:

```
Differences between 'development' and 'production':

Only in development:
  - TEST_MODE

Only in production:
  - PRODUCTION_API_URL

Different values:
  - API_KEY: 'sk_test_...' vs 'sk_live_...'
  - DATABASE_URL: 'postgresql://localhost/...' vs 'postgresql://prod-host/...'
```

## Syncing Secrets Across Environments

Add the same secret to multiple environments at once:

```bash
# Add to both development and staging
redenv sync KEY "value" --environments development,staging
```

<Callout type="info">
  This is useful for non-sensitive shared configuration like API endpoints or
  feature flags that should be consistent across environments.
</Callout>

## Environment Naming Conventions

**Recommended:**

- Use lowercase: `development`, not `Development`
- Use hyphens for spaces: `qa-testing`, not `qa_testing`
- Be descriptive: `production-eu`, not `prod-eu` (clarity over brevity)

**Avoid:**

- Special characters (except hyphens and underscores)
- Spaces
- Very long names

## Deleting Environments

While there's no dedicated "delete environment" command, you can remove all secrets:

```bash
# Switch to the environment
redenv switch env old-feature

# Remove each secret
redenv remove SECRET_NAME --all-keys
```

Or use the `drop` command to remove the entire project (all environments):

```bash
redenv drop my-app
```

<Callout type="error">
  This is destructive and cannot be undone. Use `redenv backup` first!
</Callout>

## Environment Variables in CI/CD

When deploying to different environments, set the environment name via an environment variable:

**GitHub Actions:**

```yaml
- name: Deploy to Production
  env:
    REDENV_ENVIRONMENT: production
    REDENV_TOKEN_ID: ${{ secrets.REDENV_TOKEN_ID }}
    REDENV_TOKEN_KEY: ${{ secrets.REDENV_TOKEN_KEY }}
  run: |
    # Your deployment script
```

**Vercel:**

```bash
# Set different tokens per deployment environment
# Production
REDENV_ENVIRONMENT=production
REDENV_TOKEN_ID=tok_prod_123
REDENV_TOKEN_KEY=redenv_sk_prod_...

# Preview
REDENV_ENVIRONMENT=staging
REDENV_TOKEN_ID=tok_staging_456
REDENV_TOKEN_KEY=redenv_sk_staging_...
```

## Best Practices

1. **Separate tokens per environment**: Don't use the same service token for dev and prod
2. **Use meaningful names**: Be explicit (`production`, not `prod`)
3. **Document your environments**: Keep a README explaining what each environment is for
4. **Limit who can access production**: Use read-only tokens for most services
5. **Sync configuration, not secrets**: Use `sync` for non-sensitive shared config only
6. **Backup before major changes**: `redenv backup` before cloning or bulk operations
