Secrets in Redenv are key-value pairs that are encrypted and versioned. This guide covers the fundamental operations for managing secrets.

## Adding Secrets

Add a secret to the current environment:

```bash
redenv add API_KEY "your-secret-value"
```

The secret is immediately encrypted and stored in Redis with:

- Version 1
- Your username
- Current timestamp

### Interactive Mode

For multi-line secrets or to avoid shell escaping:

```bash
redenv add DATABASE_URL
# Opens an interactive prompt
```

### From File

```bash
redenv add SSH_KEY "$(cat ~/.ssh/id_rsa)"
```

## Viewing Secrets

### View a Single Secret

```bash
redenv view API_KEY
```

Output:

```
your-secret-value
```

### List All Secrets

```bash
redenv list
```

Shows a table with keys, versions, authors, and timestamps.

### Export All Secrets

Export to `.env` format:

```bash
redenv export > .env.local
```

Output `.env.local`:

```bash
API_KEY=your-secret-value
DATABASE_URL=postgresql://...
DEBUG=true
```

<Callout type="warn">
  Exported files contain **plaintext secrets**. Never commit them to git!
</Callout>

## Editing Secrets

Edit an existing secret (creates a new version):

```bash
redenv edit API_KEY
```

Opens your default editor (`$EDITOR`) with the current value. Save and exit to update.

**Quick edit** (non-interactive):

```bash
redenv add API_KEY "new-value"
# Overwrites existing, creates version 2
```

## Removing Secrets

Remove a single secret:

```bash
redenv remove API_KEY
```

<Callout type="error">
  This removes the secret and **all its version history**. This cannot be undone
  unless you have a backup.
</Callout>

## Bulk Operations

### Import from `.env` File

```bash
# Import from file
redenv import .env.production

# Import from stdin
cat .env | redenv import
```

This reads standard `.env` format and adds/updates all keys.

### Clone Between Environments

Copy all secrets from one environment to another:

```bash
redenv clone production staging
```

## Secret Naming Conventions

**Recommended:**

- Use UPPERCASE: `API_KEY`, not `api_key`
- Use underscores: `DATABASE_URL`, not `DATABASE-URL`
- Be descriptive: `STRIPE_SECRET_KEY`, not `SSK`
- Group related secrets: `AWS_ACCESS_KEY`, `AWS_SECRET_KEY`

**Avoid:**

- Special characters (except underscore)
- Spaces
- Starting with numbers
- Reserved prefixes (unless intentional): `REDENV_`, `UPSTASH_`

## Secret Validation

Redenv doesn't enforce schemas, but you can validate in your application:

**JavaScript/TypeScript:**

```typescript
const secrets = await redenv.load();

// Validate required secrets
if (!secrets.API_KEY) {
  throw new Error("Missing required secret: API_KEY");
}

// Validate format
if (!secrets.DATABASE_URL.startsWith("postgresql://")) {
  throw new Error("Invalid DATABASE_URL format");
}
```

**Python:**

```python
secrets = await client.load()

# Use require() for fail-fast validation
secrets.require("API_KEY", "DATABASE_URL", "STRIPE_KEY")
```

## Secret Size Limits

- **Max key length**: 256 characters
- **Max value length**: 1MB (though recommended to keep under 10KB for performance)
- **Max secrets per environment**: Unlimited (limited by Redis storage)

<Callout type="info">
For very large secrets (>100KB), consider storing them in cloud storage and keeping only the URL/path in Redenv.
</Callout>

## Security Best Practices

1. **Never log secrets**: Always mask in application logs
2. **Rotate regularly**: Update secrets periodically
3. **Use read-only tokens**: For applications that only need to read
4. **Avoid hardcoding**: Never commit secrets to git
5. **Separate environments**: Different values for dev/prod
